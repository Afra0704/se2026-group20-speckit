## User Scenarios & Testing *(mandatory)*

### User Story 1 - 教師看懂正確活動時間 (Priority: P1)

教師查看活動歷史時，能分辨建立、開始與結束時間，看到與台北當地日期時間一致的紀錄，不會因部署電腦不同而出現數小時偏差。

**Why this priority**: 活動發生時間是查找正確活動及核對結果的依據；建立時間不能被誤認為結束時間。

**Independent Test**: 使用有已知事件時刻的活動，獨立核對歷史畫面的日期、時分、事件名稱與時區。

**Acceptance Scenarios**:

1. **Given** 活動結束時刻是 `2026-11-27T03:04:05Z`，**When** 教師查看結束時間，**Then** 顯示 `2026-11-27 11:04`，可從該區塊辨識「台北時間」。
2. **Given** 活動建立、開始及結束各在不同時間，**When** 查看教師活動歷史，**Then** 三者有明確標籤且各取其本身紀錄，不以建立時間或目前時間代替結束。
3. **Given** 活動仍在準備中，或從準備中直接結束，**When** 查看開始／結束欄位，**Then** 分別顯示「尚未開始」／「未開始即結束」，不捏造搶答開始時間；結束時刻若有紀錄照常顯示。
4. **Given** 完全相同的事件紀錄，**When** 分別在不同伺服器或瀏覽器時區查看，**Then** 仍顯示同一台北日期時間，不跟隨瀏覽器自行改變時區。

### User Story 2 - 新舊歷史的同一時刻一致 (Priority: P1)

教師重新查看舊活動時，已知來源的舊時間與新時間有相同解讀；無法辨識的紀錄清楚提示，其他內容仍可閱讀。

**Why this priority**: 修正不能只對新活動有效，也不能猜測舊資料而改壞歷史。

**Independent Test**: 以代表同一時刻的數種新舊表示，核對顯示一致，再以缺值及歧義紀錄檢查提示。

**Acceptance Scenarios**:

1. **Given** 有明確 UTC 或偏移量的紀錄，及有可信來源證明原為 UTC 的無時區舊紀錄，**When** 顯示同一時刻，**Then** 三者一致，不重複加上八小時。
2. **Given** 事件時刻是 `2026-11-26T16:03:07Z`，**When** 查看，**Then** 顯示 `2026-11-27 00:03`，日期跨日正確。
3. **Given** 已結束活動缺少結束紀錄，**When** 查看歷史，**Then** 顯示「時間未記錄」，而非「尚未結束」或用其他時間補上。
4. **Given** 時間格式損壞或無法證明其時區，**When** 查看，**Then** 分別顯示「時間資料無法辨識」或「時區未確認」，不顯示貌似正確的推測時間，也不使整頁失敗。

### User Story 3 - 回填相關時間與活動保持一致 (Priority: P2)

教師查看匯入確認、回填預覽、報告更新及逐格回讀時，能辨認各時間的用途；學生現有結果若含時間，也遵守同一解讀與可見範圍。

**Why this priority**: 避免活動頁已修正，回填頁仍偏差，或把預覽時間誤當來源修改時間。

**Independent Test**: 對照一個已結算活動的匯入／預覽／回填歷史，逐項核對標籤與已知時刻；不需真的重新寫入講義才能檢查既有顯示。

**Acceptance Scenarios**:

1. **Given** 匯入確認、預覽建立、作業更新及逐格回讀在不同時刻發生，**When** 教師查看對應頁面，**Then** 時間依各自語意呈現，統一至分鐘並能辨認台北時區。
2. **Given** 結算資料沒有獨立結算時間，**When** 查看結果，**Then** 不以活動結束或預覽建立時間充當結算時間；本輪不為補欄位而重建已公布結果。
3. **Given** 學生只可讀原授權範圍，**When** 查看結果，**Then** 顯示調整不新增其他組答案、教師回填資料或內部診斷內容；整堂關閉後仍沿用禁讀。

### User Story 4 - 保留原事件與結果 (Priority: P1)

教師希望只是修正看見的時間，而不是改變已發生的搶答、勝組或已保存資料。

**Why this priority**: 顯示修正不能成為重新排序或重新結算的理由。

**Independent Test**: 對照修正前後的既有活動、固定版本、有效受理順序與勝組，重新整理及重跑初始化後再次比對。

**Acceptance Scenarios**:

1. **Given** 活動已結算，**When** 重新顯示或重新啟動服務，**Then** 原活動身分、講義版本、答案原文、受理順序、順位、勝組及結果版本全部相同。
2. **Given** 使用者電腦時鐘或時區與伺服器不同，**When** 查看或提交答案，**Then** 顯示政策保持，截止及排行仍依既有受理規則，不能改用電腦顯示時間決定先後。
3. **Given** 已有教師、課程、授權與歷史資料，**When** 使用新版，**Then** 不需清資料或重新授權；可能的相容調整不得改寫原事件時刻，且重跑安全。

### Edge Cases

- UTC 跨日、跨月、跨年；帶不同合法偏移量的相同時刻；來源曾處於日光節約時間但保有明確偏移量。
- 秒與小數秒僅在畫面省略，顯示截取至分鐘，不四捨五入；原精度保持於原紀錄。
- 時間缺值、空字串、損壞文字、無法證明來源時區；未發生事件與已發生但缺紀錄須區分。
- 活動未開始即結束、重複結束、關課一併結束活動，不能因重試刷新原結束時刻。
- 既有時間已含台北偏移，不再加八小時；同名活動仍以原活動身分關聯。
- 手動改變瀏覽器時區、伺服器本地時區不同、時鐘本身不同步；顯示時區不等於校準真實時鐘。
- 權限失效、關課及重新連線，仍依原權限清除內容，不因顯示時間功能放寬讀取。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 所有本輪範圍內的事件時間 MUST 以固定「台北時間（UTC+08:00）」呈現；重新整理、不同伺服器及瀏覽器時區不得改變顯示時刻。
- **FR-002**: 可顯示的有效時間 MUST 使用 `YYYY-MM-DD HH:mm`、24 小時制；時區說明可放在區塊標題或表頭一次，不必每格重複。
- **FR-003**: 教師活動歷史 MUST 分清建立、開始及結束時間，從各自事件紀錄取得；不得用目前時間或其他事件補造。
- **FR-004**: 已有的匯入確認、預覽、作業更新及回讀時間 MUST 採相同政策並標示正確用途；不得稱為來源最近修改或結算時間。
- **FR-005**: 有明確時區的時間 MUST 保留其所代表的同一瞬間，只轉換呈現，不一律加減固定小時。
- **FR-006**: 無時區的舊時間 MUST 依可證明的來源規則解讀；只有已證明原為 UTC 的來源可按 UTC 解讀。來源未知時 MUST 顯示「時區未確認」，不得依伺服器本地時區猜測。
- **FR-007**: 未發生、未記錄與損壞的時間 MUST 區分處理，採故事 1／2 的提示；任一壞值不得使整頁無法使用。
- **FR-008**: 顯示 MUST 正確處理跨日及帶偏移量的歷史，保留原精度於原紀錄，顯示到分鐘時不進位。
- **FR-009**: 系統 MUST 保留既有資料及授權，不改寫原事件時刻或為顯示而重新結算；任何必要相容調整須可重跑、不破壞資料。
- **FR-010**: 受理順序、截止、有效答案、順位、勝組、固定講義與結果版本 MUST 維持既有規則；顯示時間不得用作另一套排行依據。
- **FR-011**: 系統 MUST 保留原教師／學生可見範圍及關課禁讀；只格式化原本可見的資料，不為學生增加教師專用紀錄。
- **FR-012**: 實作驗證 MUST 區分已重現缺陷、程式盤點風險、設計假設及尚待實測；不得把數小時偏差的使用者回報直接記為已重現八小時錯誤。
- **FR-013**: 未保存獨立事件時間的結算紀錄 MUST 維持原結果，本輪不新增假的結算時間；沒有時間的學生結果不為整齊而強制增加新事件欄位。
- **FR-014**: 同一事件重新整理、重連、關閉重試及歷史查閱 MUST 顯示同一事件時刻；既有清單排序若涉及時間，仍依實際事件先後，不能按格式化文字或不同事件的混合值改序。

### Key Entities *(include if feature involves data)*

- **事件時間紀錄**：屬於原課程、課堂、活動或回填作業的建立／開始／結束／確認／預覽／更新／回讀觀察，不代表本輪新增資料表。
- **時間來源證據**：原值的時區或可證明的產生規則，用於區分可解讀、缺值、格式損壞與來源不明。
- **顯示時間**：由事件與顯示政策取得的日期時間、事件標籤、台北時區說明及品質提示，不取代原紀錄。
- **原結果身分**：活動、講義版本、受理序列、勝組與結果版本的既有關聯；本輪只讀而不得重新產生。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 驗收矩陣中的有效時刻，100% 顯示為預期的台北日期時間；相同瞬間的不同表示完全一致。
- **SC-002**: 在 UTC、台北及另一個非台北的伺服器時區，並以不同瀏覽器時區查看同一組樣本，100% 取得相同顯示，不出現整數小時偏差。
- **SC-003**: 所有跨日／跨月／跨年、已知舊 UTC、缺值、損壞及來源不明案例，100% 符合既定結果；沒有整頁失敗或捏造時間。
- **SC-004**: 修正前後核對的既有結果，活動、講義版本、有效答案原文、順位、勝組及結果版本 100% 不變；原有授權仍可用。
- **SC-005**: 教師與至少兩組學生完成人工核對；教師能分辨建立、開始、結束、預覽及回讀的用途。參考時計與事件記錄時計已同步時，顯示的結束分鐘須落在「按下結束至收到成功回應」區間兩端各截取至分鐘所形成的含端點範圍；若跨分鐘，兩端分鐘均可能有效。自動測試仍以原始事件時刻核對轉換，不以放寬誤差代替正確性；若時計不同步則分開記錄，不冒稱時區修正可校時。

- Specify 時以台灣課堂情境提出固定台北時間為合理預設；2026-11-27 使用者原 plan 指令指定固定 Asia/Taipei、24 小時制及至秒格式；後續決策如下，取代原顯示精度。2026-11-27 使用者回報 OpenSpec 已確認時間呈現規則，並指定畫面改為到分鐘；確認者姓名與獨立紀錄未提供。若之後改為動態時區，須同步規格、三圖及驗收。
- 本輪是既有時間顯示正確性補強，不新增時區偏好設定、倒數截止、排程、時計同步服務或結算時間追補。
- 已知由標準 UTC 產生流程建立的舊紀錄可按 UTC 解讀；無來源證據的任意文字不可套用此假設。具體盤點見 [source-inventory.md](source-inventory.md)。
- 三類圖為需求層概念模型，不預定新增資料表或固定模組檔名；技術落實由 plan 以圖為藍圖決定。
