# Phase 0 研究：002 身分與活動階段

| 決策 | 理由 | 評估過的方案 |
| --- | --- | --- |
| Python 3.11 以上、Flask、Jinja、原生 JavaScript、SQLite | 延用 README 建議。本機可用同一程序服務頁面和 JSON，001／002／003 共用資料庫，無需另開前端服務。實際版本由後續環境鎖定。 | SPA 加獨立 API 增加建置與部署成本。PostgreSQL 可支援更高並行，需另行啟動服務。 |
| 每約一秒輪詢，載入、頁面恢復及重連立即重取 | 三端本機展示可先量測兩秒內更新的候選目標。單一輪詢請求進行中，採遞增狀態版本防止舊回應覆寫。斷線時提示狀態可能過期，逐步降低重試頻率。 | SSE 需要長連線及重連處理。WebSocket 的雙向連線能力超出階段同步所需。 |
| SQLite 明確短寫入交易，同檔序列化關閉、加入與成功受理 | SQLite 同一時間僅有單一寫入交易。使用 `BEGIN IMMEDIATE` 取得寫入交易後，再驗證授權和階段，避免用過期讀取做受理或允許已結束活動的新加入。SQLite 連線啟用外鍵檢查。 | 瀏覽器或請求抵達時間無法表達已確認的受理順序。程序內鎖無法涵蓋多程序連線。 |
| 短期伺服器授權，加獨立的原加入證明 | 可將一般作答授權失效與同瀏覽器的結果恢復分開。隨機恢復憑證放入同源 HttpOnly Cookie，伺服器僅儲存摘要，綁定活動及組別。結束後憑原瀏覽器證明恢復已綁定的組別。 | 僅憑自填組名無法證明曾加入，只在瀏覽器存組別識別也無法驗證原加入紀錄。 |
| 不可變 001 版本與有序題目快照 | 保留清單識別、版本、題目識別與顯示資料，使重新匯入不改變進行中活動。001 保有原版本對應的回填資訊。 | 引用最新清單會使活動題目跟著重新匯入變動。 |

防護設計包含由伺服器校驗授權與 CSRF、限制登入或代碼嘗試、祕密值排除日誌。Cookie 使用 HttpOnly、SameSite、受控期限，HTTPS 環境使用 Secure。純本機 HTTP 僅綁 loopback，使用獨立開發設定。回覆中的活動或組別 ID 僅是資源識別。

技術依據：[SQLite 交易控制](https://www.sqlite.org/lang_transaction.html) · [Flask 安全考量](https://flask.palletsprojects.com/en/stable/web-security/)

待整合的共同行為依 [Plan](plan.md) 保留。使用者已回報兩組確認同一瀏覽器的恢復範圍。
