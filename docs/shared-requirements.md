## 建議／待 OpenSpec 組確認的行為決策

| 編號 | 建議 | 理由 | 狀態 |
| --- | --- | --- | --- |
| D01 | 每組每題接受一次有效提交，空白或僅空白字元不受理，重送不產生新順位 | 規則容易解釋，可避免連點及重試改變結果 | 待確認 |
| D02 | 「最快」按伺服器成功受理順序判定，以後端交易統一處理階段檢查、去重與順位 | 兩組同時提交及截止邊界能得到唯一結果 | 待確認 |
| D03 | 活動採準備、搶答中、已結束三階段，結束後拒收新答案 | 方便同步與驗收截止邊界 | 待確認 |
| D04 | 學生以活動碼與組別代碼加入，教師具獨立的操作授權 | 降低本機展示的登入工作量，同時區分操作權限 | 待確認 |
| D05 | 依題目記號及填空格記號動態建立對應，遇到重複、缺漏或歧義時要求修正；具體語法看完範本再定 | 避免誤判題數及寫錯格位，讓兩組共用格式 | 待確認 |
| D06 | 結束後學生可看勝組、答案與順位；教師可看全部組別結果 | 讓公布範圍明確，方便 CSV 與講評共用資料 | 待確認 |
| D07 | 無人提交的題目回填時略過，填入答案前預覽目標；來源有變更時重新辨識及確認 | 保留未作答格並降低版面變動造成的誤寫 | 待確認 |
| D08 | 勝組代表搶答順位勝出，教師自行講評答案內容 | 符合作業以最快組別選答案的描述，避免額外擴張自動評分 | 待確認 |
| D09 | 斷線重連後重取活動狀態；重試回填時，相同值可視為已完成，不同內容須提示確認 | 讓重試有可驗證的結果 | 待確認 |
| D10 | 一題含多個填空或有題組時，如何計算題數、提交與選勝組，需看完範本後定案 | 避免題號、空格與題組數量混用 | 待確認 |

### SpecKit 內部建議

以下內容由 SpecKit 組定案，兩小組共同驗收使用者行為即可。

- 技術棧建議 Python、Flask、Jinja、原生 JavaScript、SQLite，原因是本機執行與依賴較容易管理。
- 初期以約一秒輪詢同步活動狀態，正常本機操作以兩秒內更新為建議驗收目標，須實測後確認。
- 子功能建議拆為 001 講義匯入與回填、002 身分與活動階段、003 搶答與結果；各自維護 spec、plan、tasks 與對應圖。
- 模型依課堂教學可用 Luna 做主要開發、Sol 做分析與補漏，依帳號可用模型及用量調整。

## 額外功能與加分取捨

| 功能 | 來源與建議優先度 | 理由 | 狀態 |
| --- | --- | --- | --- |
| CSV 結果匯出 | 課程列出的額外功能，建議第一優先 | 可共用結算資料，清楚展示題號、組別答案、順位與勝組 | 待兩組確認 |
| 匿名答案講評 | 創意建議，CSV 完成後評估 | 結束後教師可投影匿名答案比較，再公布勝組，支援課堂討論 | 待兩組確認 |
| 題組匯入與整組提交 | 課程列出的額外功能，核心完成後評估 | 貼近題組範本，需同步調整匯入、提交、排序與回填 | 待兩組確認 |
| 更公平的順位機制 | 課程列出的額外功能，最後評估 | 可鼓勵未勝組參與，須先確認規則、與最快勝出核心要求的相容方式及測試 | 待兩組確認 |

基本分數為文件 30%、程式碼 25%、Demo 20%、組別評量表 15%，合計 90%。兩小組分別繳交的項目平均後計入大組成績。額外與創意功能、GitHub branch／PR 協作、SpecKit 子功能拆分均可加分。上台報告加分 5%–20%，以小組報名、限四組，超額由 Demo 投票篩選，逾期補交組不得報名，細節依課程後續通知。

## 建議共同驗收情境

| 編號 | 情境 | 追溯與預期 |
| --- | --- | --- |
| A01 | 匯入單題範本副本 | R02，逐題核對題數與題號 |
| A02 | 換一份題數不同、移動欄列的講義，並完成回填 | R10–R11，全部勝組答案進入對應填空格，其他內容保持原值 |
| A03 | 教師開始、兩組學生作答、結束與公布 | R01、R03–R09，三方走完整流程 |
| A04 | 學生檢視搶答中的頁面及 API | R06，僅收到自己的可見資料 |
| A05 | 兩組近乎同時提交，同組重送 | R07 與 D01–D02 定案規則，勝組唯一且順位穩定 |
| A06 | 開始前、空白、結束後及與關閉同時的提交 | D01–D03 定案規則，受理與拒絕結果可解釋 |
| A07 | 沒有人作答，或匯入後講義被修改 | D05、D07 定案規則，避免錯誤回填 |
| A08 | 重新整理、斷線重連及重試回填 | R08、D09 定案規則，狀態與資料一致 |

測試紀錄應包含執行者、日期、版本或 commit、輸入、預期、實際結果及截圖或日誌。尚未定案的情境先確認預期，尚未執行的測試標記為未執行。
